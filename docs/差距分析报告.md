**最关键的三个差距（补全前会导致"文档写的功能实际不可用"）**

1. **校验门禁形同虚设（FR4.4）**：`POST/PUT /api/rules` 直接落库，从不跑 `verify`；前端只调 `/parse`。文档要求"校验不通过的规则禁止入库"。
2. **含 `var` 的规则一律校验失败（FR5）**：`/verify` 用 `DataDictionary::default()`，任何 `var` 都被判 `UNDEFINED_VAR`。`cargo run -- verify examples/with_var.rules` 实际失败，README 却声称可跑通。
3. **`rule_versions` / `rule_triggers` 从不写入（FR7/FR10）**：文档要求"每条规则带 version/owner/effective_date，AST 与校验报告落库"，代码里 rules 表有列、server 不写。

## 2. 本次补全的功能点（逐项：文档依据 → 原状 → 方案 → 涉及文件 → 接口/数据结构 → 关键逻辑 → 验证）

### 2.1 规则保存形式化校验门禁（FR4.4）

- **原状**：`POST /api/rules`、`PUT /api/rules/:id` 不做任何校验直接落库；前端 `saveRule()` 只调 `/parse`。
- **方案**：新增 `gate_rule()`，在落库前跑 parse + `Verifier::verify_report()`；`errors` 非空即返回 `{error, status:"FAIL", errors[], warnings[]}` 且不写库。
- **文件**：`crates/rules-server/src/main.rs`
- **接口**：`POST /api/rules`、`PUT /api/rules/:id` 响应新增 `errors` / `warnings` / `status`
- **关键逻辑**：`if !report.is_ok() { return Err(json!({...禁止入库...})) }`（errors 阻断，warnings 放行）
- **验证**：单测 `rule_save_is_gated_by_verification`；冒烟"门禁拒绝未声明实体规则 PASS"（含 `UNDEFINED_ENTITY` 明细）

### 2.2 结构化分级校验报告（FR4.4 / 设计 §4.4）

- **原状**：`/verify` 仅返回 `{ok, errors:[string]}`，无法区分 error / warning。
- **方案**：verifier 新增 `VerifyIssue{kind,severity,message,contracts}` 与 `VerifyReport{errors,warnings}`；按设计分级——覆盖缺口/未登记 var/冗余规则为 **warning**，其余为 **error**。
- **文件**：`crates/rules-verifier/src/lib.rs`、`crates/rules-server/src/main.rs`
- **接口**：`POST /verify[?rule_id=N]` → `{ok, status:"PASS|FAIL", errors:[{kind,severity,message,contracts}], warnings:[...]}`
- **关键逻辑**：`VerificationError::is_warning()` 定义分级；`verify()`（全量问题，兼容旧调用）与 `verify_report()`（分级）双入口
- **验证**：单测 `coverage_gap_is_warning_not_error`、`verify_route_reports_warnings_without_blocking`；冒烟 `POST /verify 结构化报告 PASS`

### 2.3 `var` 保守策略与绑定接入（FR5 / §7.3 / FR14）

- **原状**：未登记 `var` 被当成硬错误；server 校验时不加载任何绑定，含 `var` 的规则永远被拒。
- **方案**：① 未登记 `var` 降级为 warning（设计 §7.3"未登记的 var 打 WARNING"）；② server 校验时把该规则 `rule_bindings` 里已绑定的 `var_name` 注册进字典，未绑定者产生提示；③ CLI 用占位值登记全部 `var`（保守假设任意取值）。
- **文件**：`crates/rules-verifier/src/lib.rs`、`crates/rules-server/src/main.rs`、`crates/rules-cli/src/main.rs`
- **数据结构**：`DataDictionary{ vars, signals, external_bindings }` ↔ DB `rule_bindings(rule_id,var_name,datasource_id,table_name,column_name)`
- **验证**：`cargo run -- verify examples/with_var.rules` → `OK: verification passed.`（补全前失败）；冒烟"var 未绑定 → UNDEFINED_VAR 提示但不阻断 PASS"

### 2.4 类型检查：未声明实体 / 未声明 signal / 字符串与数值比较（FR3）

- **原状**：仅检查未声明状态与未定义 var；`contract C on Account`（Account 未声明）、`"abc" > 3.0`、`SomeUnknown(1.0)` 全部放行。
- **方案**：verifier 新增 `check_entities` / `check_signals` / `check_types`；内置函数白名单 `is_builtin_call()`（now/DaysOverdue/count/avg/…）与 `spec.signals` 声明合并判定。
- **错误类型**：`UNDEFINED_ENTITY`、`UNDEFINED_SIGNAL`、`TYPE_MISMATCH`
- **验证**：单测 `hard_errors_block_verification`、`type_mismatch_between_string_and_number_is_reported`、`unknown_function_call_is_reported`

### 2.5 冗余规则检测（FR4.1"不可达分支"的保守子集）

- **原状**：无。
- **方案**：同实体 + invariant/guard/transition/severity/message 全等 → `REDUNDANT_CONTRACT`（warning）
- **验证**：单测 `duplicate_contract_is_redundant_warning`

### 2.6 规则版本与触发器落库（FR7 / FR10）

- **原状**：`rule_versions` / `rule_triggers` 表存在但 server 从不写入；`ast_json`、`verify_report` 无处可查。
- **方案**：新增 `save_version()`（version = `COALESCE(MAX(version),0)+1`，写 dsl_text / ast_json / verify_report / submitted_by）与 `save_trigger()`（`INSERT … ON DUPLICATE KEY UPDATE`）；内存模式以 `MemState.versions/triggers` 等价模拟。
- **接口**：新增 `GET /api/rules/:id/versions`
- **验证**：单测 `rule_save_writes_version_and_trigger`；冒烟"版本列表""版本含 AST JSON""二次保存版本递增到 2"

### 2.7 规则字段与校验触发模式（FR7 / FR9.1–9.3）

- **原状**：`Rule` DTO 只有 name/group_id/dsl/mode/cron，读到 status/owner 缺失；前端保存时硬编码 `mode:'LIFECYCLE', cron:''`，无 mode 选择 UI。
- **方案**：后端 `validate_rule_input()` 校验 `mode ∈ {LIFECYCLE, ONCE}`、`ONCE` 必须带 cron；读写补 `status` / `owner`；前端新增 mode 下拉 + cron 输入（ONCE 时显示并必填）。
- **验证**：单测 `once_mode_requires_cron`；冒烟"ONCE 缺 cron 被拒 PASS"

### 2.8 数据源完整 CRUD + 真实连接探测 + schema 三级树（FR8.1 / FR8.2）

- **原状**：只有 `GET/POST /api/datasources`；`POST /api/datasources/:id/test` 是写死的 `{"ok":true,"message":"连接成功"}`；没有 structure 接口，前端页无操作列。
- **方案**：新增 `PUT` / `DELETE /api/datasources/:id`、`GET /api/datasources/:id/schema`；`test` 改为**真实连接**（sqlx 动态建连 → 查 `information_schema.TABLES`）；`schema` 返回 `[{table, columns:[{name,type}]}]`。
- **文件**：`crates/rules-server/src/main.rs`（`probe_datasource` / `load_schema` / `connector_url`）、`web/src/views/DatasourcesView.vue`
- **关键逻辑**：5s 连接超时；`db_type != mysql` 明确返回"暂不支持在线探测"，不谎报成功；编辑时密码留空表示沿用旧值
- **验证**：冒烟"真实连接探测成功（发现 7 张表）""schema→table→column 三级树 PASS"

### 2.9 变量 → 列绑定（FR8.3 / FR14）

- **原状**：绑定面板完全缺失；`POST /api/bindings` 是纯 INSERT，重复提交会撞唯一键报错。
- **方案**：① 后端改为 upsert（`ON DUPLICATE KEY UPDATE`）+ 新增 `DELETE /api/bindings/:id` + `GET /api/bindings?rule_id=` 过滤生效；② 前端 `RulesView` 右侧新增绑定面板：自动识别 DSL 中的 `var xxx` 与 `when` 条件里的裸标识符，逐个下拉选择"数据源 → 表 → 列"。
- **文件**：`crates/rules-server/src/main.rs`、`web/src/logic/dsl.js`（新增 `extractBindingTargets`）、`web/src/views/RulesView.vue`
- **关键逻辑**：`extractBindingTargets()` 提取比较式两侧的裸标识符，排除关键字/内置函数/实体/流/信号/`let`/signal 形参/状态名；字符串字面量先置空避免 `emit:"a > b"` 误判
- **验证**：vitest 新增 4 例（`extractBindingTargets` describe）；冒烟"upsert 绑定""绑定 upsert 幂等（同 rule+var 仅 1 行）PASS"

### 2.10 动作类型白名单与删除（设计 §12.1 告警动作页）

- **原状**：`action_type` 任意字符串都收；无删除接口。
- **方案**：白名单 `sms / http / email / state_transition`；新增 `DELETE /api/actions/:id`；前端加删除列 + JSON 配置校验提示
- **验证**：单测/冒烟"动作类型白名单校验 PASS"

### 2.11 派生指标 signal 运行时求值 + 内置函数补全（FR1.2 / FR2）

- **原状**：`signal` 只解析不执行——runtime 的 `Call` 分支只硬编码 `now/DaysOverdue/max/count`，用户声明的 `signal Foo(x)=…` 取到 0.0；`ratio/avg/sum/min/abs` 缺失。
- **方案**：runtime 构造时把 `spec.signals` + `dict.signals` 合并为 `signals: HashMap<name,(param,expr)>`；`Call` 未命中内置时走 signal 分派，用 `RefCell<HashMap<String,f64>>` 做形参临时绑定后递归求值；补齐 `min/abs/ratio/sum/avg`。
- **文件**：`crates/rules-runtime/src/lib.rs`
- **关键逻辑**：形参绑定"入栈—求值—还原"，避免嵌套调用污染外层
- **验证**：单测 `signal_declaration_is_evaluated_at_runtime`（`Doubled(3.0)=6.0 > 5.0` 触发告警）

### 2.12 `state == <状态名>` 谓词（FR2 / 设计 §2.2 示例）

- **原状**：`state` 与状态名都是普通 `Ident`，`eval_scalar` 双双取 0.0 → `state == SUSPENDED` 恒真，`until(always(state == SUSPENDED), …)` 语义错误。
- **方案**：`state_comparison_target()` 识别 `state == X` / `X == state`，改为字符串比较实体当前状态
- **验证**：单测 `state_comparison_predicate_matches_entity_state`

### 2.13 `entity key:` 字段驱动实体路由（FR1.1）

- **原状**：runtime 忽略 DSL 里的 `key:`，一律用 `<实体名小写>_id`（`Company` → `company_id`）；`key: code` / `key: account_id` 形同虚设，事件归属判断同样用错字段。
- **方案**：新增 `key_fields()` —— `key:` 声明优先，兼容回落 `<lower>_id`；`ingest()` 与 `event_belongs_to_entity()` 统一改用候选键列表
- **验证**：新增单测 `entity_declared_key_routes_events_to_instance`、`company_key_code_still_drives_historically_window`

### 2.14 告警命中轨迹增强（FR7 / FR6）

- **原状**：`Alert.trace` 只在发生状态转移时有一条 `state`，无法回答"哪个 temporal 子式为真"。
- **方案**：trace 恒定携带 `now`、`invariant = VIOLATED (摘要)`（`summarize_temporal()` 生成人类可读摘要）、`guard_value`，再叠加状态转移；CLI `demo` 打印全部 trace
- **验证**：单测 `signal_declaration_is_evaluated_at_runtime` 断言 trace 含 `guard_value`/`invariant`；CLI demo 输出实测

### 2.15 Web 校验报告页（设计 §12.1）

- **原状**：设计要求的 `verify.html`（校验报告页）缺失；`/verify` 接口在 UI 中从未被调用。
- **方案**：新增 `web/src/views/VerifyReportView.vue` + 顶部导航"校验报告"：选规则 → 实时跑 `/verify` 展示 errors/warnings 分级卡片 + `rule_versions` 版本历史（含各版本校验结论与 DSL 快照）
- **验证**：`npm run build` 通过；`RulesView` 内嵌的校验面板与保存门禁同源

### 2.16 真实缺陷修复（非文档条目，但阻塞上述功能）

| 缺陷 | 现象 | 根因 | 修复 |

## 5. 假设

1. `mode` 语义按 FR9 表：`LIFECYCLE` = 订阅式（CDC 事件驱动），`ONCE` = 定时快照；`mode` 缺省为 `LIFECYCLE`。
2. **校验严格度**：errors 阻断入库；warnings（覆盖缺口、未登记 var、冗余规则）仅提示。依据设计 §4.3 与 §7.3。
3. `var` 在运行时按"未解释符号"保守建模：未绑定不阻断，绑定后参与求值（与设计 §4.3 一致）。
4. 每次规则保存（含无内容变化的 PUT）都产生一个 `rule_versions` 快照，version 单调递增。
5. 数据源连接探测超时 5s；探测失败/不支持类型必须显式报错，不得返回伪成功。
6. 实体实例键：`entity.key` 优先，`<entity_lowercase>_id` 作为兼容回落（历史规则文件与测试沿用 `company_id`）。
7. `emit` 文案中的 `>`、`<` 等字符不影响绑定识别（扫描前先清空字符串字面量）。

## 8. 范式重构：从产生式规则到时序约束（v2）

### 8.1 背景：为什么要脱离 Drools 模式

原 DSL 的核心是 `contract X on E { invariant: ... violation {...} }`，但这层皮下面仍然是
**LHS → RHS 的产生式规则**：

- **状态与计算割裂**：事实（Fact）离散进入，`ctx.disclosure.days_overdue` 要由微服务在外部算好；
  规则引擎退化为"单纯的 if-else 计算器"。
- **时间不是一等公民**：`timestamp` 只是事实的一个字段，没有时序算子语义，
  滑动窗口聚合只能靠外部预计算。
- **校验维度浅**：无法在语言层面回答"跨时间维度的状态转移是否完备"、
  "时序事件是否可能产生因果死锁"。
- **执行模型重**：RETE / PHREAK 在每次事实插入后重跑网络，运行期仍依赖反射与节点匹配。

### 8.2 目标范式：四类一阶公民

| # | 概念 | AST 节点 | 语义 |
|---|------|---------|------|
| 1a | **Entity** | `EntityDecl` / `TransitionDecl` | 实体生命周期 + 确定性状态迁移边 |
| 1b | **Metric** | `MetricDecl` / `MetricBody` | 动态派生信号流（滑动折叠 / 流聚合 / 带 guard 标量） |
| 2 | **Stream & Event** | `StreamDecl` / `StreamOp` / `Lambda` | 事件流算子：投影 / 过滤 / 关联 / 窗口 / 折叠 |
| 3 | **Temporal Invariant** | `SpecDecl` / `TemporalExpr` | 度量时序逻辑 MTL：Always / Eventually / Within / Until / Since / Implies |
| 4 | **StateMachine & Violation** | `TransitionDecl` / `ViolationHandler` | 违规 = 状态迁移，而非脚本副作用 |

`SpecFile { entities, streams, metrics, specs }` 取代了旧的
`SpecFile { entities, streams, signals, vars, contracts }`；
`ContractDecl` / `VarDecl` / `SignalDecl` 三个节点被删除，`TemporalExpr::WithinOp` 与
`Historically{...within: DurationLit}` 旧形态被统一到 `{ expr, within: Option<Expr> }`。

### 8.4 执行层下沉（性能）

```
Expr        ──装载期──► FlatProgram { ops: Vec<FlatOp>, num_slots, text_slots, field_slots }
TemporalExpr ──装载期──► TemporalAutomaton { nodes: Vec<AutoNode>, atoms: Vec<Atom> }
```

1. **零递归、零 AST 遍历**：`AutoNode` 以后序布局存放，**子节点索引恒小于父节点索引**，
   因此 `step()` 只需一次 `for i in 0..nodes.len()` 的前向扫描，状态写在
   `truth: Vec<u8>` / `latch: Vec<u8>` / `pending: Vec<u8>` / `timers: Vec<i64>`。
2. **原子谓词分流**：`AtomKind::Flat(FlatProgram)` 走原生字节码；
   含函数调用（`now()` / `days_between()`）或事件字段路径的谓词退化为
   `AtomKind::Scalar(Expr)` / `AtomKind::Event(Lambda)`，直到 WASM 后端把 `Call` 下沉。
   `flat_atom_ratio()` 可观测快路径占比。
3. **字符串驻留**：`Interner` 让文本相等退化为 `u32` 比较（id 0 保留给空串 = "该操作数是数值"）。
   装载期额外预驻留**枚举常量**（状态名 / 字面标识符 / 路径末段），
   修复了 `state == SUSPENDED` 因 id 未命中而误落到数值比较的缺陷。
4. **扁平内存布局（SoA）**：配对槽 `fields_num: Vec<f64>` + `fields_text: Vec<u32>`，
   `FlatVm::swap_fields()` O(1) 换入换出，无反射、无指针追逐。
5. **环形缓冲区**：`RingBuffer` 定长、O(1) push / 覆盖最旧 / `evict_before()`，
   窗口扫描是顺序内存遍历。
6. **事件驱动**：`ingest()` 在事件落地**同一拍**完成"投影入环 → 实体路由 → 推进状态机"；
   `tick()` 只处理纯时钟推进（截止期到期）。

### 8.5 时序模型检验（补位"Drools 校验维度浅"）

**A. 状态转移完备性**（`check_transition_completeness`）

| 编码 | 触发条件 | 级别 |
|---|---|---|
| `UNREACHABLE_STATE` | 从 `initial` BFS 不可达 | warning |
| `STUCK_STATE` | 非终态却无出边 | warning |
| `TERMINAL_STATE_HAS_EDGE` | 终态仍有出边 | error |
| `UNDEFINED_TRANSITION_DRIVER` | `transition ... on: X` 指向不存在/实体不一致的 spec | error |
| `UNDECLARED_TRANSITION` | spec 的 `transition:` 与实体声明的边不一致 | error |
| `TRANSITION_DRIVER_MISMATCH` | 边的 `on:` 绑定与 spec 不一致 | warning |

**B. 因果死锁**（`check_causal_deadlocks` / `scan_deadlocks`）

| 编码 | 触发条件 | 级别 |
|---|---|---|
| `CAUSAL_DEADLOCK_UNTIL` | `until(p, q)` 的 q 恒假 | error |
| `CAUSAL_DEADLOCK_EVENTUALLY` | `eventually/within(p)` 内 p 恒假 | error |
| `UNSATISFIABLE_INVARIANT` | 不变量整体恒假 | error |
| `IMPOSSIBLE_CONSEQUENT` | `implies` 前提恒真且结论恒假 | error |

> 判定基于保守常量折叠（`eval_static` / `eval_expr_static` 三值逻辑）；
> `rules-smt` 的 Z3 接口接入后可从"保守判定"升级为"完备判定"。

### 8.6 兼容性

旧语法全部自动 desugar，既有 `.rules` 文件与已交付文档无需改动：

| 旧 | 新 |
|---|---|
| `contract X on E` | `spec X on E` |
| `signal f(x:T)->T = e` | `metric f(x: T) -> T := e` |
| `var n = e` | `metric n := e` |
| `Stream[T]` | `Event[T]` |
| `stream X = …` | `stream X := …` |
| `rule X on E when P then{…}` | `spec X on E { invariant: always(not (P)) … }` |
| `exists(S)` | `S.exists()` |

覆盖测试：`legacy_syntax_desugars_to_new_ast`、`rule_when_then_sugar_desugars_to_spec`。

### 8.7 仍存留的差异（v2）

| # | 缺口 | 性质 |
|---|---|---|
| P1 | **Z3 未真接入**：时序模型检验是保守常量折叠，非完备判定 | 接口预留（`rules-smt`），已声明降级 |
| P2 | **LLVM / WASM 状态机编译未实现**：当前是原生 Rust 字节码快路径 | 接口预留（`AtomKind::Flat`） |
| P3 | **Join / CoGroup 仅解析未执行**：runtime 未实现两侧流的关联运算 | 未实现 |
| P4 | **`eventually` / `within` 的"未来承诺"仍依赖 tick 推进**，没有独立的定时回查 scheduler | v1.5 |
| P5 | `rules-dictionary` 仍保留 `vars` / `signals` 两个字段名（属于"外部数据源绑定"概念，与 DSL `metric` 不同层），未随 AST 重命名 | 命名遗留 |
